# CharOCR 0/O 定向返工结果

更新于 2026-09-27。`formal-v1` 在 MAA v6.18.0 完整分析器中把真实关卡 `0-1` 识别为 `O-1`；`formal-v2` 已修复该问题。五条 WordOCR 路线没有重训或改包。

## 做了什么

- 从发布任务 `StageDrops-StageName` 的 ROI `[140,60,200,55]` 和阈值 `[210,255]` 提取开发裁剪，再按前景边界加 3 像素留边收紧。Linux 的 `0-1` 探针输入实际为 **67×32** 的原色/二值裁剪，formal-v1 均输出 `O-1`，官方均输出 `0-1`。Windows 的 **200×55** 原始 ROI 三方都正确；两条记录的输入不同，不能据此判定平台差异，也不能把手工收紧裁剪称为发布任务的精确输入。完整 StageDrops 分析器在两端均复现 formal-v1 的 `O-1` 并确认 formal-v2 修复，支持 Char 识别路径的业务修复结论。
- 从固定版本 `MaaAssistantArknights/MaaTestSet@dfb2238c` 选取并目视核对 `0-1`、`OF-F4`、`10-3`、`10-16` 四张真实结算图，生成 448 张确定性轻量变体。所有来源、ROI、阈值、标签、复核者、参数和哈希均写入 spec；这些图片只允许用于开发训练，禁止进入独立验收。
- 从正式 Char step-500 权重开始，以学习率 `2e-6` 训练 300 步，每 100 步执行导出一致性和 MAA 原生接口门禁。4,800 次曝光中真实困难样本占 186 次；其余仍按旧版关卡号、费用和 ASCII 配比采样。
- step 100、200、300 都通过门禁并修复 `0-1`。三者质量相同时保留最早的 step 100，减少对已有权重的扰动。

## 当前边界

Linux v6.18.0 的模型、导出、真实裁剪和完整分析器已通过。Windows 端增量报告确认两层资源隔离、`0-1`、孤立数字 `0`、真实费用 `0` 和原业务集无新增回归，结论为 `pass_cn_integration`；详细证据见 [Windows formal-v2 增量验证结果](windows-formal-v2-result.md)。繁中、英文、日文和韩文仍缺对应客户端的新实图独立验收；性能继续只记录，不作本轮合并门槛。
