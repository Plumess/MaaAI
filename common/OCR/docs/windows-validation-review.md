## 独立复核内容

- 重新计算交付 ZIP、候选 ZIP、13 张截图和候选包内 12 个资源的 SHA-256，均与清单一致。
- 独立比较 `official-output.json` 与 `candidate-output.json`：忽略置信度后，10 个主业务输出完全相同。
- 检查 0/O 最终有效 ROI 和原始日志：候选 `O` 的置信度为 0.9096，官方 `0` 为 0.7901；同一裁剪经过 `NumberOcrReplace` 后都返回 `0`。前两组包含斜杠边缘的诊断已被报告正确排除。该现象与此前 Linux 协作验证记录的 3 条 Char 原始 `0→O` 一致，并非 Windows 平台新引入。
- 重新汇总 12,000 次热调用和 40 个冷进程，P50、P95、响应时间比率与 Windows 报告一致，无丢弃轮次或失败调用。
- 比较 Windows 探针与原探针源码：变化限于导出入口、Windows 路径转换和编译警告设置，未改识别器、业务分析器或任务规则。

## 风险边界与下一步

数字任务通常使用 `NumberOcrReplace`，本次费用业务输出没有失败。但 CharOCR 也用于未必执行该替换的文字，例如关卡号和部分账号匹配，所以不能仅凭费用规则把原始 `0→O` 全面视为安全。

下一步先用当前正式候选补一组真实 Char 关键样本：含 `0` 的完整关卡号（如 `0-1`、`1-10`）、完整费用 0 画面，以及能区分字母 `O` 与数字 `0` 的文本。若出现业务错误，只返工 Char 数据和微调；五条 Word 路线无需重训。若这些实际路径均正确，再由维护者决定是否把验收口径明确为最终 MAA 业务结果。

本次模型推理使用 v6.18.0 同源码 Release 测试 DLL；ONNX Runtime、FastDeploy、OpenCV 和 DirectML DLL 与发布包逐字节一致，但测试 `MaaCore.dll`、`MaaUtils.dll` 因增加探针而与发布包哈希不同。官方发布核心只完成了资源注册检查，GUI 交互启动和未修改发布核心的内部推理没有直接测试，应作为集成限制保留。


## 2026-09-27 补充：已确认完整业务回归

为判断原始 `0→O` 是否会越过 MAA 规则影响实际任务，我用同一正式候选和 MAA v6.18.0 原生分析器补跑 4 张既有真实开发图。`10-3`、`OF-F4` 和完整费用 0 均正确；日服完整关卡 `0-1` 的官方结果为 `0-1`，候选结果为 `O-1`。

该图片曾用于开发，只用于定位问题，不作为新的独立准确率样本。但它调用完整 `StageDropsImageAnalyzer`，且 `O-1` 已包含连字符，现有“无连字符再试 WordOCR”的回退不会执行。因此风险从“原始诊断混淆”升级为“已观察到的完整业务回归”。

## 2026-09-27 补充：formal-v2 已在 Linux 与 Windows 关闭回归

我只返工 Char，并冻结五条 WordOCR。formal-v2 step 100 在同一真实图上返回 `0-1`，同时保持 `OF-F4`、`10-3`、`10-16` 和费用 `0`；120 张 Char guard 全部正确，10 项冻结国服业务回放无新增差异。formal-v2 相对 formal-v1 只变化 Char ONNX。Windows formal-v2 增量回放随后通过：官方到 v2 恰有 12 个允许资源变化，v1 到 v2 仅 Char ONNX 变化；`0-1`、孤立数字 `0` 和更正后的真实费用 `0` 均正确，原业务集无新增变化。最终结论为 `pass_cn_integration`。随后官方发布版 GUI 又完成公招和仓库两项国服黑盒识别；这不扩大到 `0-1` 或战斗费用 `0` 的 GUI 验收。详见 [Windows formal-v2 增量验证结果](windows-formal-v2-result.md) 与 [CharOCR 0/O 定向返工结果](char-rework-result.md)。
